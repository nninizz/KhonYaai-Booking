## BR-02-01 (AI เสนอ รอทีมยืนยัน): การตรวจ OTP

Decision Table: ประเมินตามแถวจากบนลงล่าง แถวแรกที่ตรงเป็นผลของการตรวจรหัส

| แถว | เหตุการณ์ / เงื่อนไข | ผลที่ยืนยันแล้ว | สถานะ / หมายเหตุ |
|---|---|---|---|
| R1 | ขอ OTP ใหม่ | จำลองส่ง SMS ไปยัง `users.phone` และใช้ OTP mock `123456`; API ส่งค่า `mock_otp` ตาม contract แต่ UI ไม่เปิดเผยรหัส; ช่องกรอกเริ่มว่าง; ขอได้ทันทีและไม่จำกัดจำนวนครั้ง; OTP เดิมยังใช้ได้จนหมดอายุ | กฎที่ยืนยันแล้ว; อายุของแต่ละ issuance เริ่มนับเมื่อแสดง flow กรอก OTP; ไม่มีการเชื่อม SMS provider จริง; การแยกหลาย issuance และจำนวนครั้งผิดแยกชุดยังเปิด (Q-02-04) |

| R3 | ตรวจรหัสที่ตรงและยังไม่หมดอายุ | ยืนยัน OTP สำเร็จ; หากเป็นการยืนยันครั้งแรกให้ตั้ง `users.is_verified` เป็น `true` | กฎยืนยันจากคำตอบ Q-02-07; บัญชีที่ `is_verified=true` ไม่ต้องยืนยัน OTP ซ้ำเมื่อ login; สำหรับบัญชีที่ยังไม่ verified token ออกเมื่อ flow login สำเร็จ แต่รูปแบบและ lifecycle ยังไม่กำหนด |

## BR-02-02 (AI เสนอ รอทีมยืนยัน): ค่าและอายุ OTP

OTP เป็นตัวเลข 6 หลัก โดย Backend ใช้ค่าจำลองคงที่ `123456`; API contract คงส่ง `mock_otp` แต่ UI ไม่แสดงค่า คำใบ้ หรือ placeholder ที่เปิดเผยรหัส และช่องกรอกเริ่มว่าง. อายุ OTP คือ 15 นาที การส่ง SMS เป็นการจำลองเท่านั้น ไม่มีการเชื่อมต่อ SMS provider จริง

สถานะ: รายละเอียดข้างต้นและจุดเริ่มนับอายุเมื่อ mock SMS/OTP แสดงผลทีมยืนยันแล้ว; วิธีแยก OTP หลายคำขอและนับจำนวนครั้งผิดแยกชุดยังต้องถามตาม Q-02-04.

Trace: REQ-FN-201, REQ-FN-205; AC-02-01, AC-02-06.

## BR-02-03 (AI เสนอ รอทีมยืนยัน): การขอ OTP ใหม่

ผู้จองขอ OTP ใหม่ได้ทันทีโดยไม่จำกัดจำนวนครั้ง รหัสก่อนหน้ายังคงใช้ได้จนหมดอายุ การขอใหม่จำลองการส่ง SMS และใช้ค่า OTP mock คงที่ `123456`; UI แสดงช่องกรอกว่างโดยไม่เปิดเผยค่านั้น.

สถานะ: จำนวนครั้ง การไม่มีช่วงรอ การคงอายุรหัสเดิม และการเริ่มนับอายุรหัสใหม่เมื่อแสดงผลยืนยันแล้ว; วิธีแยก OTP หลายรายการที่ยังไม่หมดอายุและนับจำนวนครั้งผิดแยกชุดยังต้องถามตาม Q-02-04.

Trace: REQ-FN-201, REQ-FN-205; AC-02-01, AC-02-06.

## รายละเอียดที่ยังไม่กำหนด

- วิธีระบุ OTP หลายคำขอที่ใช้ค่า `123456` พร้อมกัน และนับจำนวนครั้งผิดแยกต่อชุด (Q-02-04)
- พฤติกรรม response หรือ HTTP status ในกรณี OTP ถูกต้อง ผิด หมดอายุ หรือผิดครบ 3 ครั้ง (Q-02-09)
- รายละเอียด token ที่ออกหลังยืนยันสำเร็จ (Q-02-05)
- request/response, validation และ error/status ของ login, verify OTP และ `/me` (Q-02-03, Q-02-09)
- การคงค่า `is_verified` หลัง backend restart; ยังไม่มีคำตอบหรือการตัดสินใจเรื่อง persistence

## คำยืนยันทีมที่เกี่ยวข้องกับ Auth

รายการนี้บันทึกคำตอบทีมโดยตรง ไม่ได้เปลี่ยนสถานะ BR-02-01 ถึง BR-02-03 จาก “AI เสนอ รอทีมยืนยัน”:

- ผู้จองที่ `is_verified=true` login ด้วย email/password ได้โดยไม่ทำ OTP ซ้ำ; ได้ token เมื่อ flow login สำเร็จ. ผู้จองที่ยังไม่ verified ต้องผ่าน OTP ก่อนออก token (Q-02-05, Q-02-07).
- `is_verified` หมายถึงเบอร์โทรผ่าน OTP mock และตั้งเป็น `true` หลังยืนยันครั้งแรกสำเร็จ; ไม่เกี่ยวกับการตรวจบัตรประชาชนหรือใบหน้า (Q-02-07).
- `/api/auth/me` ส่งเฉพาะ `id`, `name`, `email`; ไม่ส่ง `phone`, `password`, OTP, token หรือ `is_verified` (Q-02-06).
- ผู้ใช้ mock ที่มีอยู่ทั้งหมดใน `backend/app/mock_db.py` ได้รับอนุมัติเป็น fixtures (Q-02-08).
- การตรวจ AC-02-05 ใช้หลักฐาน config/dependency และ mock data ใน RTM โดยไม่มี Gherkin Scenario; การบันทึกหลักฐานไม่ใช่ผลทดสอบหรือการยืนยันว่า implementation ครบแล้ว.
