## 1. Intent

ผู้จอง (ลูกค้า) ที่ยังไม่มีบัญชีต้องสร้างบัญชีด้วย **ชื่อ อีเมล เบอร์โทร และรหัสผ่าน** ก่อนใช้ระบบจองรถขนย้ายของ
เมื่อสมัครสำเร็จ ระบบเพิ่มผู้ใช้ใหม่ใน `users` โดยตั้ง `is_verified = False` แล้วส่งผู้ใช้ไปหน้า Login ของ ②
② รับ email/password; สำหรับบัญชีที่ยังไม่ยืนยัน ② เริ่ม OTP ทางเบอร์โทรและเมื่อ OTP ถูกต้องจึงออก token; บัญชีที่ยืนยันแล้ว login โดยไม่ทำ OTP ซ้ำ
feature นี้ไม่ส่งหรือตรวจ OTP และไม่ออก token (เป็นของ ②)
อ้างหลักฐาน: ยังไม่มี PB-xx / EV-xx (ดู Q-03)

## 2. Scope และ Non-goals

In:
- ฟอร์มสมัครสมาชิก 4 ช่องที่ `/register` และ `POST /api/auth/register` (REQ-FN-101, REQ-FN-105)
- ตรวจรูปแบบข้อมูล (REQ-FN-102) และตรวจอีเมล/เบอร์ซ้ำ (REQ-FN-103)
- เพิ่มผู้ใช้ใหม่ใน `users` ของ `mock_db.py` กลาง ตั้ง `is_verified = False` (REQ-FN-104, REQ-DAT-101)
- ไม่ส่ง `password` กลับ และไม่ออก token (REQ-PRV-101, REQ-SEC-101)
- หลังสมัครสำเร็จส่งต่อไปหน้า Login ของ ②; ② เป็นผู้เริ่มและตรวจ OTP ระหว่าง login (REQ-FN-106)
- กันกดซ้ำระหว่างส่งคำขอสมัคร (REQ-FN-107)

Non-goals:
- ส่ง/ตรวจ OTP, login ด้วย email/password หลังยืนยัน, ออก token, `get_current_user()`: เป็นของ ② (AS-01, AS-02)
- การคำนวณราคา มัดจำ จองล่วงหน้า ยกเลิก (BR-01 ถึง BR-07): เป็นของ ③ ④ ⑤ ⑥
- ลืมรหัสผ่าน แก้ไขโปรไฟล์ ลบบัญชี: ไม่ทำในโปรเจกต์นี้
- สมัครฝั่งคนขับ: ไม่ทำ ระบบทำเฉพาะฝั่งผู้จอง
- ส่งอีเมลหรือ SMS ยืนยันตอนสมัคร: ไม่ทำ (OTP เป็นของ ② และเป็น mock)
- ฐานข้อมูลจริง: ใช้ mock ตาม REQ-CON-101; เก็บ password ตามค่าที่รับมาใน mock เพื่อให้ตรงกับ Auth ปัจจุบัน (D-01-02)

### สัญญา API

`POST /api/auth/register` **ไม่ต้องมี** `Authorization` (REQ-SEC-101) error ใช้ร่วมกันทั้งกลุ่ม: 409 สถานะไม่ถูกต้อง | 422 ข้อมูลไม่ถูกรูปแบบ (ตาม SPEC-04)

Request (JSON)
```json
{ "name": "สมชาย ใจดี", "email": "somchai@mail.com", "phone": "0899999999", "password": "Abcd1234" }
```

| ผล | HTTP | body |
|---|---|---|
| สำเร็จ | 201 | `{ "id": 2, "name": "สมชาย ใจดี", "email": "somchai@mail.com", "phone": "0899999999", "is_verified": false }` (ไม่มี `password`) |
| อีเมลหรือเบอร์ซ้ำ (BR-RG-05, 06) | 409 | `{ "detail": "อีเมลนี้ถูกใช้สมัครแล้ว", "field": "email" }` หรือ `{ "detail": "เบอร์โทรนี้ถูกใช้สมัครแล้ว", "field": "phone" }` |
| ข้อมูลผิดหรือขาด (BR-RG-01 ถึง 04) | 422 | `{ "detail": [ { "loc": ["body", "phone"], "msg": "เบอร์โทรต้องเป็นตัวเลข 10 หลัก ขึ้นต้นด้วย 0" } ] }` ชื่อฟิลด์อยู่ตัวสุดท้ายของ `loc` มีรายการเดียวต่อฟิลด์ที่ผิด **ไม่มีคีย์ `input`** และไม่มีคำนำหน้า "Value error, " |

- `field` ใน 409 เป็นคีย์ที่ **AI เสนอเพิ่ม** (เพิ่มได้โดยไม่ทำให้คนที่อ่านแค่ `detail` พัง) เพื่อให้หน้าจอวาง error ใต้ช่องที่ถูกต้องโดยไม่ต้องเดาจากข้อความ (D-01-06)
- 422 รูปแบบ `detail` เป็นรายการ ส่วน 409 เป็นข้อความต่างกัน; status code เป็นแนวทางร่วม แต่ response body เป็นไปตามแต่ละ feature (D-01-06)
- ค่าที่ผู้ใช้ส่งมาไม่ถูกสะท้อนกลับใน response ใด ๆ (BR-RG-09)
- เมื่อ frontend ได้ 201 ให้ส่งผู้ใช้ไป `/login` ของ ②; ① ไม่ส่งหรือตรวจ OTP เอง. ② ใช้ `POST /api/auth/login` รับ email/password และเริ่ม OTP สำหรับบัญชีที่ยังไม่ยืนยัน; `POST /api/auth/verify-otp` ตรวจ OTP และคืน token เมื่อสำเร็จ (REQ-FN-106)
